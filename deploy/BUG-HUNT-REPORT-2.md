## [CRITICAL] Owner-Rolle liest gesamte Tenant-Buchhaltung (Rechnungen/Kunden-PII) ohne Owner-Self-Scope
- **Ort:** `apps/api/src/features/buchhaltung/router.py:47` · Dimension: auth-scope
- **Problem:** Alle Buchhaltungs-Leseendpunkte sind nur mit `require_lodgify_permission(Permission.OWNER_REPORTING)` (`_read = _write`) geschützt. Die owner-Rolle BESITZT diese Permission (lodgify_permissions.py:122-129, _OWNER enthält OWNER_REPORTING). Der Buchhaltungs-Service scopt aber ausschließlich per `tenant_id` (`_require_tenant`, service.py:130-133) und kennt KEINEN Owner-Self-Scope (kein is_owner/owners.user_id-Filter, grep nach is_owner/owner in service.py leer). Damit liest ein eingeloggter Eigentümer über GET /buchhaltung/customers, /invoices, /companies/{id}, /quotes, /number-sequences die kompletten Finanz- und Kunden-PII-Daten (Name/Adresse/Steuer-ID) ALLER Objekte/Kunden des Tenants — nicht nur seine eigenen. Das verletzt §4.2 (Owner sieht nur eigene Daten). Anders als owner_statements/service.py (das mit _owner_self_id/_require_statement_visible korrekt self-scopt) fehlt hier jede Owner-Einschränkung.
- **Szenario:** Owner-User (role=owner, OWNER_REPORTING vorhanden) mit gültigem JWT ruft GET /api/v1/buchhaltung/customers auf → erhält list_customers_array(ctx), gefiltert nur nach tenant_id → vollständige Kundenliste des Tenants inkl. fremder Kunden-PII.

## [CRITICAL] Finalisierte Rechnungen sind löschbar → GoBD-Verstoß + Nummern-Wiederverwendung
- **Ort:** `apps/api/src/features/buchhaltung/service.py:1088` · Dimension: trace-geld
- **Problem:** delete_invoice() blockiert nur bei is_locked=true, setzt sonst deleted_at='now()' (Soft-Delete). is_locked hat DB-Default false (0023_buchhaltung_fundament.sql:95) und wird NIRGENDS im gesamten Code je auf true gesetzt (grep über apps/ bestätigt: keine einzige Zuweisung). Damit ist JEDE finalisierte, nummerierte Rechnung — auch die Pflicht-Rechnung aus dem Check-out (create_from_reservation, status 'finalized'/'paid') — dauerhaft löschbar. Zusätzlich deckt der GoBD-Backstop-Index invoices_tenant_number_uidx (0105_number_sequences_race.sql:78-80) nur Zeilen mit deleted_at IS NULL ab: nach dem Soft-Delete fällt die Zeile aus dem Unique-Index → dieselbe invoice_number kann einer neuen Rechnung erneut vergeben werden.
- **Szenario:** Betreiber erzeugt beim Check-out RE-0007 (finalized, is_locked=false). Später DELETE /api/v1/invoices/{id} → 204, deleted_at gesetzt. RE-0007 verschwindet aus dem Unique-Index. Eine neue Rechnung (manueller Flow, client-gelieferte invoice_number, oder ein künftiger Zähler-Rücklauf) kann RE-0007 ein zweites Mal tragen. Ergebnis: verschwundener Beleg + doppelte Rechnungsnummer, beides GoBD-widrig.

## [HIGH] Stale ari_outbox row can re-open a genuinely booked day (no supersession guard)
- **Ort:** `apps/api/src/features/channel_manager/ari_push.py:685` · Dimension: channex-ari
- **Problem:** process_ari_outbox() selects ALL status='pending' rows ordered by created_at and pushes each row's absolute availability value to Channex, with no check whether a NEWER outbox row (or a newer live push) for the same (property_id, overlapping date range) has already superseded it. push_availability_for_property likewise never marks older pending rows for the same days as obsolete. Because availability pushes for the same days are 'last-writer-wins' at Channex but the outbox has no per-(property,date) coalescing/freshness ordering, a stale free-up (availability=1) can be pushed AFTER a newer block (availability=0) already went live. try_enqueue_ari explicitly does NOT dedup availability jobs (disjoint-range rationale), so nothing upstream collapses them either.
- **Szenario:** 1) OTA booking blocks days D -> outbox R1 (avail=0) pushed live -> done. 2) That booking is cancelled -> bookings_sync.py:320 creates outbox R2 (avail=1, no outbox_id) but the live Channex call FAILS -> R2 stays 'pending'. 3) A new booking B blocks the same days D -> outbox R3 (avail=0) pushed live -> done. 4) process_ari_outbox tick runs, finds R2 still 'pending', pushes avail=1 for days D to Channex -> the now genuinely-booked day D is re-opened at the OTAs -> double-booking risk. The absolute-value idempotency argument does not hold across two DIFFERENT intended values for the same days.
