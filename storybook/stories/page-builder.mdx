# Page-Builder

Der Page-Builder ist der Multi-Tenant-White-Label-Website-Builder von myNextDays: Jede Agentur baut im Dashboard eine mehrseitige eigene Website in einem **Framer-artigen visuellen Editor** und veröffentlicht sie unter der **eigenen Custom-Domain**. Der Vorsprung gegenüber reinen Website-Buildern: die **Buchungs-Engine ist ein einbettbarer Block** (Suche, Objekt-Grid) — keine getrennte Welt.

Die Nachbauten der Editor-Oberfläche liegen in der Rubrik **Page-Builder** (Editor-Toolbar, Seiten-Panel, Ebenen-Baum, Insert-Panel, Einfügen-Menü, Font-Picker, Zoom-Leiste).

# Page builder

The page builder is myNextDays' multi-tenant white-label website builder: every agency composes its own multi-page website in a **Framer-style visual editor** inside the dashboard and publishes it on its **own custom domain**. The edge over generic builders: the **booking engine is an embeddable block** (search, property grid) — not a separate world.

## Editor-Modell vs. Persistenz-Modell (wichtig)

Der Editor ist bewusst weiter als das Speicherformat — das ist dokumentierter Ausbau-Stand, kein Versehen (Bau-Vorlage: `docs/FRAMER-FEATURES.md`):

| Editor (craft.js) | Persistenz (site_blocks) |
| --- | --- |
| Hierarchischer Node-Baum, freie **Frames** (x/y/Breite/Höhe), Container **Stack/Grid/Masonry** | Flache, geordnete Liste der **10 Block-Typen** |
| Page-**Variablen** mit Bindungen, **Code-Overrides**, Effekte (Hover/Scroll/Parallax) | nicht persistiert (In-Memory im Editor) |
| Voller Stil-Inspektor (Pins, Size-Modi, Radius je Ecke, Schatten, …) | `settings`: Hintergrund, Padding, volle Breite, Opazität, Sichtbarkeit, Radius, Drehung |

Beim Speichern übersetzt `serialize.ts` den Baum in die flache Blockliste; Layout-Container und ihre Kinder gehen dabei **verloren**. Der öffentliche Renderer kennt nur die 10 Block-Typen.

For previewing unpublished drafts there is an **HMAC-signed draft token** (`POST /pages/{id}/draft-token`, TTL 1 h): `builder/app/render/[pageId]` renders drafts with it — no JWT ever enters an iframe. The postMessage bridge to the editor exists as infrastructure but is **not wired up** in the current editor (the editor renders the nodes directly).

## Editor model vs. persistence model (important)

The editor intentionally runs ahead of the storage format (build spec: `docs/FRAMER-FEATURES.md`):

| Editor (craft.js) | Persistence (site_blocks) |
| --- | --- |
| Hierarchical node tree, free-floating **frames** (x/y/width/height), **stack/grid/masonry** containers | Flat, ordered list of the **10 block types** |
| Page **variables** with bindings, **code overrides**, effects (hover/scroll/parallax) | not persisted (in-memory in the editor) |
| Full style inspector (pins, sizing modes, per-corner radius, shadows, …) | `settings`: background, padding, full width, opacity, visibility, radius, rotation |

On save, `serialize.ts` flattens the tree into the block list; layout containers and their children are **dropped**. The public renderer only knows the 10 block types.
