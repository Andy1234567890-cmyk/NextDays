## Mandantenfähigkeit & RLS

Jeder Vermieter ist ein Tenant. Die Isolation läuft über Row-Level-Security (RLS) in Postgres, nicht über Anwendungslogik (Pool-Modell, geteiltes Schema mit `tenant_id`). Die `tenant_id` steht im JWT `app_metadata`; der globale auth-Slice nutzt die Service-Role und umgeht RLS bewusst beim Onboarding.

<Mermaid
  title="Mandantenfähigkeit & RLS — Control Plane vs. Application Plane"

    SLICES -->|"SQL mit JWT-Claim"| DB
    AUTH -.->|"Service-Role (umgeht RLS)"| DB`}

## Kritische Flows — 7.1 Registrierung (atomar mit Rollback)

Die Registrierung legt Tenant und Nutzer atomar an: Scheitert die User-Anlage, wird der Tenant per Rollback wieder gelöscht. Erst bei Erfolg entsteht eine Session.

<Mermaid
  title="7.1 Registrierung (atomar mit Rollback)"
  chart={`sequenceDiagram
    actor L as Vermieter
    participant API as FastAPI (auth)
    participant SR as Supabase (Service-Role)
    participant DB as Postgres

    L->>+API: POST /api/v1/auth/register
    API->>+SR: INSERT tenant (Service-Role)
    SR->>DB: tenants
    DB-->>SR: tenant_id
    SR-->>-API: tenant_id
    API->>+SR: create_user(app_metadata={tenant_id, role:owner})
    alt User-Anlage scheitert
        SR-->>API: Fehler
        API->>SR: DELETE tenant (Rollback)
        API-->>L: 409 / 500
    else ok
        SR-->>-API: user_id
        API->>SR: INSERT users-Row
        Note over API,DB: Bei Fehler: User + Tenant zurückrollen
        API->>API: login()
        API-->>-L: 201 + SessionResponse
    end`}
/>

## Kritische Flows — 7.2 Direktbuchung mit Double-Booking-Schutz

Bei einer Direktbuchung sperrt der calendar-Slice die Tage per `SELECT ... FOR UPDATE` atomar. Ein einziger Kalender verhindert Double-Bookings: Sind Tage belegt, antwortet die API mit 409 Conflict.

<Mermaid
  title="7.2 Direktbuchung mit Double-Booking-Schutz"
  chart={`sequenceDiagram
    actor Guest as Gast
    participant Web as Web (Next.js)
    participant API as FastAPI
    participant Cal as calendar-Slice
    participant DB as Postgres

    Guest->>+Web: Buchungsanfrage
    Web->>+API: POST /api/v1/booking-engine/reserve
    API->>+Cal: Verfügbarkeit prüfen
    Cal->>+DB: SELECT availability FOR UPDATE
    DB-->>-Cal: Tages-Status
    alt Termine frei
        Cal-->>API: OK, Tage gesperrt
        API->>DB: INSERT reservation (pending)
        Note over API,DB: EIN Kalender = kein Double-Booking
        API-->>Web: 201 Created
        Web-->>Guest: Bestätigung
    else belegt
        Cal-->>API: Konflikt
        API-->>Web: 409 Conflict
        Web-->>Guest: "Nicht verfügbar"
    end
    deactivate Cal
    deactivate API
    deactivate Web`}
/>

## Reservierungs-Lifecycle (State)

Der `reservation.status` ist eine echte State-Machine: von Pending über Confirmed (mit Unter-Zuständen vom Check-in bis Completed) bis Cancelled. Bereits ab Pending sind die Kalendertage gegen Double-Booking gesperrt.

<Mermaid
  title="Reservierungs-Lifecycle (State)"
  chart={`stateDiagram-v2
    [*] --> Pending: Buchung angelegt
    Pending --> Confirmed: Zahlung erhalten
    Pending --> Cancelled: Timeout / Storno

    state Confirmed {
        [*] --> AwaitingCheckIn
        AwaitingCheckIn --> CheckedIn: Gast reist an
        CheckedIn --> Completed: Aufenthalt endet
        Completed --> [*]
    }

    Confirmed --> Cancelled: Stornobedingung
    Cancelled --> [*]

    note right of Pending
        Kalendertage gesperrt
        gegen Double-Booking
    end note`}
/>

## Deployment & Skalierung

DSGVO-konform und self-hosted bevorzugt mit EU-Datenresidenz als harter Grenze. Das zustandslose FastAPI skaliert horizontal hinter einem Load Balancer; aller State (Postgres, Redis, Queue, OCR/Storage) ist externalisiert und bleibt in der EU. EU-überschreitende Kanten sind mit Transfer-Rechtsgrundlage annotiert.
